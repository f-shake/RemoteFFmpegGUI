### 实测（Playwright + 真 WebAPI + 临时库，2026-09-12）

- **空闲 8 秒内 `/api` 请求数为 0**（改造前每 3 秒 4 个）。
- **反复进出任务页 5 次**：每次恰好 2 个请求（`GET Task` + `GET Queue/State`），不累加（改造前每进一次多一个永不停的 3 秒轮询）。
- **一次真实队列运行**（AV1 1080p）：进度每秒推送（`percent`/`fps`/`time`/`size`/`speed` 全部在动）；暂停/继续/停止即时生效；**14 秒内只有 1 次快照请求**（10 秒一次的设计节奏）。
- **不经 UI 从外部加任务**：任务列表自动刷新（1 个 `GET Task`，无人工操作）——推送链路 `TaskService → 通知器 → 广播服务 → Hub → 浏览器` 全通。
- **四态圆点**：停掉服务 → 黄点闪烁约 16 秒 → 蓝点（进入轮询）→ 21 秒内红点（轮询也失败）；重启服务 → 回蓝（**不自动重连**）；刷新页面 → 变绿。

### 与计划的偏差（都已落地，记录在案）

1. **枚举去掉 `Standalone`**：它的数据库影响（任务被置为进行中 / 执行结束落库）已被 `Tasks` 覆盖，多一个没人用的成员是死代码。
2. **挂钩全放服务层**，没有挂 `TaskRepository.UpdateStatusAsync`：否则"取消/重置"会经服务层与仓储层各通知一次；仓储层只做数据访问，通知属应用层。
3. **计划时间的通知点**从 `QueueTimerCallback` 挪到 `RunQueueAsync` 开头的 `scheduleTime = null`：到点触发与手动"开始队列"都会清空计划时间，一处覆盖两种情形。
4. **补了 3 处计划没列的通知**：任务执行结束落库后（`ProcessTaskAsync` 的 finally，且放在 `RemoveManager` **之后**，保证推送出去的快照与"管理器已清空"一致）、队列异常标记任务为错误之后、任务被置为进行中（放在 `AddManager` 之后，此时快照才有 `isProcessing: true`）。
5. **`QueueStateProvider.CreateStatus()` 在"管理器存在但 ffmpeg 进程未启动"时把 `IsProcessing` 置 true**：否则点"开始队列"后状态栏会收起再弹出。
6. **五态而非四态**：多一个灰色的 `connecting`（首次连接中），避免用绿/红说谎。
7. **乐观更新加 `issuedSeq` 守卫**：实测发现推送常常**先于 HTTP 响应**到达（队列已跑完），此时才做的乐观更新会盖回旧值且再无推送纠正——状态栏会永久停在"处理中"（旧代码由 3 秒轮询掩盖）。见「八之三」。
8. **`SnapshotCache` 不依赖任何服务**（纯键值 + TTL + LRU，生成逻辑留在控制器里），并且放在 `Core/Caching/`（注册仍只在 WebAPI，WPF 不受影响）——这样单元测试能直接测它的并发与淘汰行为。

- **`UnsafeQueueUserWorkItem` 不流动 ExecutionContext** → 改用 `QueueUserWorkItem`（成本差异可忽略，将来给队列加 Serilog `LogContext` 时不会丢日志上下文）。
- **计划时间的跨线程读**：复验指出"把推送丢到线程池"这一步让 `scheduleChanged` 的读**新增**了一次跨线程读（`DateTime?` 是 16 字节结构体，理论上可撕裂）。已把这次读挪回**写入线程**（`OnTaskChanged` 里读一次再带进线程池）。至于 `QueueService.scheduleTime` 本身——它在定时器线程与 HTTP 请求线程上的读是**既有**行为、本轮没有加重，故不改其表示（改成 `long ticks`/`ToBinary` 需要额外处理 `DateTimeKind`，反而是给"计划时间跑偏 8 小时"这种真 bug 开门）：1 秒一次的读窗口下撕裂概率处于天文量级，且下一次推送/轮询会自愈。
9. **`seq` 从当前毫秒时间戳起步**（而非 0）：服务端重启后新序号一定大于旧序号，否则前端会因"只接受更大的序号"永久丢弃新状态、界面冻住。

全前端**没有任何 `clearInterval`**（只有 `useIsMobile.ts:18`、`CodeArguments.vue:249` 清理 resize 监听），而 `router-view` 没有 `keep-alive`（`App.vue:85-89`）：

### 目标

1. 队列状态由服务端推送（SignalR），轮询降级为兜底；
2. 前端引入 pinia，让实时状态有唯一持有者（**先 pinia 后 SignalR**，避免先写一遍临时 props 再搬）；

### 请求体积（决定"必须瘦身"）

`GET api/Queue` 返回 `StatusDto`（`QueueController.cs:14-19`），运行中**约 1.5~3 KB**，因为 `StatusDto.Task`（`StatusDto.cs:199`）是**完整 `TaskEntity`**，其中：

- `FFmpegArguments` 是**整条命令行**（二次编码因 `FFmpegTaskService.cs:456` 用 `;` 拼接而翻倍）；
- `Message`（质量对比任务含 SSIM/PSNR/VMAF 多行）、`Output`/`RealOutput`、`CreateTime`/`StartTime`/`FinishTime`。

**按原样每秒推一条 ≈ 10 MB/小时/客户端**，比现状（3 秒一条 × 两条 = 约 7.2 MB/小时）**更费**。所以推送前必须裁剪。

## 一、总体设计

```
ffmpeg stdout ──> FFmpegTaskService.StatusChanged（约 0.5 秒一次）
                        │
Core（纯类库，不含 ASP.NET）│
  ├─ 新增单例 ITaskChangeNotifier ◀── TaskService / TaskRepository（瞬时）发「任务表变了」
  │                              ◀── QueueService（单例）发「队列起止 / 计划时间」
  │
WebAPI                      │
  └─ RealtimeBroadcaster（HostedService，单例）
        ├─ 订阅 ITaskChangeNotifier ──> tasksChanged / scheduleChanged（事件驱动）
        └─ 处理中每 1 秒采样 queue.MainQueueManager.GetStatus() ──> queueStatus（瘦身）
                    │
                    └──> IHubContext<QueueHub> ──> 所有浏览器（进程内广播）
                                                      │
前端（pinia）                                   HubConnection（仅 WebSocket）
  └─ stores/queue.ts ◀── queueStatus / tasksChanged / scheduleChanged
                      ◀── 降级时：HTTP 轮询 GET api/Queue/State
```

**分层原则**：Core 只负责"广播事件/提供状态"，不引用任何 ASP.NET 类型；WebAPI 负责"翻译成 SignalR 消息"。这样 WPF（进程内直连 Core）不受任何影响。

### 3.3 鉴权中间件（自己写，MVC 过滤器管不到 Hub）

插在 `app.UseRouting()`（`:251`）**之前**，与 `:234-247` 的内联中间件同风格：

```csharp
app.Use(async (context, next) =>
{
    if (context.Request.Path.StartsWithSegments("/api/queue-hub"))
    {
        var token = appSettings.Value.Token;
        if (!string.IsNullOrEmpty(token))
        {
            // 顺序：Cookie（前端 api.ts:8 已把 token 存在 cookie，同源握手自带，不进访问日志）
            //   → access_token 查询参数（跨域/dev/将来 WebView 的兜底，与隔壁 TinySyncNote 同款）
            string provided = context.Request.Cookies["token"];
            if (string.IsNullOrEmpty(provided))
                provided = context.Request.Query["access_token"];
            provided = provided?.Trim();
            if (provided?.StartsWith("Bearer ", StringComparison.OrdinalIgnoreCase) == true)
                provided = provided["Bearer ".Length..];
            if (provided != token)
            {
                Log.Warning("实时通道鉴权失败：IP={Ip} Path={Path}",
                    context.Connection.RemoteIpAddress, context.Request.Path);
                context.Response.StatusCode = StatusCodes.Status401Unauthorized;
                return;   // 在升级连接之前拒绝
            }
        }
    }
    await next();
});
```

要点：

- **路径判断用的是剥完 `PathBase` 之后的 `Request.Path`**（`UsePathBase` 在 `:209`，早于此中间件），所以 `/ffmpeg/api/queue-hub` 与 nginx 剥前缀后的 `/api/queue-hub` **两种部署形态都能命中**。
- 规则与 `AppActionFilter` 一致：`Token` 为空则完全不校验（本地调试即如此）。
- **失败必须落日志**（带 IP）——否则握手静默 401 无从排查。
- 浏览器 `WebSocket` 无法自定义请求头，这是绕过限制的通用做法（隔壁两个仓库同样处理，SpatialQuery 还专门写了注释）。

### 3.4 保活

- 用 SignalR 默认值（`KeepAliveInterval` 15 秒、`ClientTimeoutInterval` 30 秒），**不写应用层心跳**：15 秒一次的 ping 已足够挡住反代 idle 超时，且空闲时不需要额外发消息（正符合"空闲不发"的约定）。
- nginx 的 `proxy_read_timeout` 必须 > 15 秒（默认 60 秒即可）。

### 3.5 广播服务 `RealtimeBroadcaster`（HostedService）

```csharp
public class RealtimeBroadcaster(IHubContext<QueueHub> hub,
                                 QueueService queue,
                                 TaskRepository taskRepository,
                                 ITaskChangeNotifier notifier) : BackgroundService
```

- **事件驱动部分**：订阅 `notifier.Changed`
  - `Tasks` → 广播 `tasksChanged`，载荷 `{ reason, hasPending }`（顺带把 `hasPending` 一起发过去，前端就不用再问一次）
  - `QueueStarted` / `QueueFinished` / `Standalone` → 立刻广播一次 `queueStatus`（不等下一个采样点，保证"点开始"立刻有反馈）+ `tasksChanged`
  - `Schedule` → 广播 `scheduleChanged`，载荷 `{ scheduleTime }`
- **节拍采样部分**：`PeriodicTimer` 1 秒
  - `queue.MainQueueManager != null` → 采样 `GetStatus()`，转成瘦身 DTO 后广播 `queueStatus`
  - 空闲 → 不发（连接靠 SignalR 自身 ping 保持）
  - 采样时若与上一条内容完全相同（可用序列化后的字符串比对），跳过发送，进一步省流量
- 所有广播包 `try/catch` 包住并记日志：**推送失败绝不能影响队列执行**。

## 六、前端：单例 realtime 模块与降级链路

### 6.1 `src/utils/realtime.ts`（模块级单例，**不引入额外状态库**）

```ts
const url = new URL(getUrl('queue-hub'), document.baseURI).toString()
const connection = new HubConnectionBuilder()
  .withUrl(url, {
    skipNegotiation: true,                       // 只走 WebSocket：降级由我们的轮询兜底，不要 SignalR 传输层回退
    transport: HttpTransportType.WebSockets,
    accessTokenFactory: () => Cookies.get('token') ?? '',   // 作为 access_token 查询参数附带
  })
  .withAutomaticReconnect([2000, 4000, 8000])    // 2/4/8 秒，三次
  .build()
```

- 地址**显式用 `new URL(...)` 解析成绝对地址**，不依赖客户端对相对路径的处理：PROD 时 `getUrl` 返回 `api/queue-hub`，跟随 `<base href="/ffmpeg/">` 解析出 `/ffmpeg/api/queue-hub`；DEV 时 `getUrl` 本身就是 `http://localhost:5001/api/queue-hub`。两种部署形态都不用另写拼接逻辑。
- 导出：`connect()`（幂等）、`on(type, handler)`（返回退订函数）、`close()`。
- 生命周期：顶层布局挂载时 `connect()`、卸载时 `close()`（照 SpatialQuery 的 `AppLayout.vue:197/160` 写法）。
- `onreconnected` → 连接状态回 `ws`，并**立刻向服务端要一次全量**（见 6.3）；`onclose` → 进入 `http` 降级（见 6.2）。

### 6.2 降级：`http` 轮询

- 重连序列（2/4/8 秒）用尽后 `onclose` 触发，**永久转入 HTTP 轮询**：调 `GET api/Queue/State`，**处理中 3 秒一次、空闲 15 秒一次**。
- **不再自动重连**，只有**刷新页面**才会重新尝试 WebSocket（按你的决定）。
- **标签页不可见时暂停轮询**（监听 `document.visibilitychange`），切回来立即补一次。
- 轮询也失败（沿用现有 `netError` 语义，`App.vue:13` 的文案）→ 连接状态 `failed`。

### 6.3 状态覆盖的顺序问题

推送与轮询可能短暂并存（重连成功的那一瞬）。**覆盖规则**：服务端在每条 `queueStatus` 里带一个自增序号（`seq`），前端只接受**序号更大**的消息；HTTP 轮询用同样的序号字段参与比较，避免旧数据盖掉新数据。

### 6.4 任务页订阅

- `tasksChanged` 到达 → `stores/queue.ts` 里的 `tasksVersion++`；`Tasks.vue` `watch(tasksVersion)` 后**去抖 200 毫秒**再 `fillData()`（保留现有分页/筛选/勾选/展开逻辑，一行不改）。
- **处理中不再需要"每 3 秒拉列表"**：进度由推送更新；列表由事件驱动。
- 顺手删掉 `Tasks.vue` 自己那条重复的队列请求（`refreshQueueStatus`/`refreshHasPending` 与其调用点）。

## 八之三、阶段 2~5 实测发现并修复的问题（2026-09-12）

用 Playwright + 真 WebAPI（临时库、临时输入输出目录）跑真实队列时抓到两个只靠读代码很难发现的时序问题：

1. **推送先于 HTTP 响应到达，乐观更新把真实状态盖回旧值**（本轮最严重的一处）
   - 现象：点"开始队列"、任务跑完后，底部状态栏一直停在"处理中"，只有刷新页面才消失。
   - 抓到的 WebSocket 帧：`queueStatus(seq=31, isProcessing=false)` → `queueStatus(seq=32, isProcessing=false)` → 随后 POST 的响应才到 → `applyOptimisticCommand('start')` 把状态写成 `{...当前(seq=32), isProcessing:true}`。
   - 根因：`StartQueue` 是"发射后不管"，服务端的通知与推送在控制器返回**之前**就发出去了；等浏览器处理完 POST 响应，真实状态早已是最新的。旧代码靠 3 秒轮询在 3 秒内纠正，改成纯推送后**再没有任何东西会来纠正它**。
   - 修复：命令发出前先记下状态序号（`queue.currentSeq()`）随命令传入，乐观更新时若发现期间已有更新的状态（`lastSeq > issuedSeq`）就放弃这次预测；另外在操作后的补刷里追加一次 `refreshState()` 兜底（覆盖"队列里已无待处理任务、根本不会开始跑"这类没有推送可来的情况）。

2. **"管理器已建立但 ffmpeg 进程未启动"时 `isProcessing` 为 false**
   - `StatusDto` 的 `StatusDto(task)` 构造函数不置 `IsProcessing`，而 `Manager.GetStatus()` 在 `Process == null` 时用的正是它。
   - 现象：点开始后状态栏先出现、随即被一条 `isProcessing:false` 的推送收起来，几百毫秒后才回来（与问题 1 叠加时就变成"永久收起"）。
   - 修复：推送用的状态统一由 `QueueStateProvider.CreateStatus()` 生成，凡"主队列管理器存在"就按 `IsProcessing = true` 上报。

另有一个环境坑（与代码无关、但影响排障）：`dotnet build <单个项目>.csproj` 的输出目录是 `Generation/bin/<项目名>`，而**解决方案构建**是 `Generation/bin/Debug/<项目名>`（`Directory.Build.props` 的 `OutputPath` 用了 `$(Configuration)`，单独构建项目时该属性为空）。直接运行 `Generation/bin/Debug/.../WebAPI.exe` 时若只构建过单个项目，跑的就是旧二进制——怀疑"改了没生效"时先核对 DLL 时间戳。

## 十三、风险与前提

1. **nginx 必须加 WebSocket 升级头**（最高优先级）：

   ```nginx
   location /ffmpeg/ {
       proxy_pass http://127.0.0.1:5001/;
       proxy_http_version 1.1;
       proxy_set_header Upgrade $http_upgrade;
       proxy_set_header Connection "upgrade";
       proxy_read_timeout 300s;   # 必须 > SignalR 的 15 秒 ping 间隔
   }
   ```

   隔壁 SpatialQuery 的部署文档就**漏了这三行**（它只写了 SSE 的 `proxy_buffering off` 与 `Connection ''`，后者恰好与 WS 所需的 `Connection: upgrade` 冲突）。不配的话症状是"本地绿点、外面永远蓝点"的**静默降级** —— 功能可用，但实时性丢失且不易察觉（这正是四态圆点的价值）。

2. **单实例前提**：广播走进程内 `IHubContext`，多实例部署时各实例的客户端收不到彼此的变化。
3. **IIS in-process 托管**（发布包里有 `web.config`）需要服务器启用 WebSocket 功能；**Windows 服务模式不受影响**。按你的部署形态确认即可。
4. **前端无测试框架、无 lint**：pinia 迁移与推送改造只能靠 `vue-tsc` + 手工清单，改动面又覆盖多个页面 —— 这是本计划最大的质量风险，务必按第 0/1/4 阶段的顺序分步验证。
5. **`MapFallback` 的陷阱**：Hub 路径若不在 `/api` 下会被回退成 200 + index.html（SignalR 客户端会拿到 HTML 而非 404，难以排查）。
6. **推送绝不能影响执行**：`RealtimeBroadcaster` 的每次广播都要 `try/catch`，异常只记日志。
