# 数据库版本化迁移管道（数据库版本 = 程序版本）

## 背景与目标

现状：`SimpleFFmpegGUI.Core/Compatibility/DatabaseMigrator.cs` 的 `MigrateIfNeeded(connStr)` 是唯一迁移入口，内含 6 步**内联线性脚本**，一次事务包裹，成功后写 `_MigrationHistory` 版本 1。被 3 处调用（`WebAPI/Program.cs:206`、`WPF/App.xaml.cs:62`、`WebTest/CompatibilityMigrationTests.cs:42`），均在 `EnsureCreated()` 之前。

问题：
1. 未来加 v3 只能改这份主函数，无法"叠加扩展"。
2. `_MigrationHistory` 只有整数 `Version`（永远 =1），无 `< N` 分支。
3. **缺口**：全新库由 EF `EnsureCreated()` 创建（`Program.cs:94` / `App.xaml.cs:73`），**不写 `_MigrationHistory`**。未来任何迁移器以"无历史表"当"旧库"判定时，会把纯新库误判成 v1。

**本方案核心约束**：**数据库版本跟随程序版本**。程序版本可能以补丁/小版本前进（如 v2.0.1、v2.1.0），而非固定整版路径（v3）。因此版本表示必须支持**语义版本（major.minor.patch）**，且某次发布若不动 schema，则**不产生迁移**，DB 停在旧版本。

## 已核实事实

- `_MigrationHistory`：`(Version INTEGER PRIMARY KEY, MigrationDate TEXT, Description TEXT)`，当前只写版本 1（`DatabaseMigrator.cs:286-304`）。
- 调用顺序：迁移在 `EnsureCreated` 之前；`EnsureCreated` 仅在"无任何表"时才建表，遇到已有表的库是 no-op。
- 已发出的 v2.0 版本库写的是**整数** Version（值 1），且已完成 v1→v2（`Arguments` 已改名 `Parameters`）。
- `PresetConverter.ConvertFromV1_1` / `OldModels.cs` 已抽到 `Compatibility/`，旧 DTO 平铺、无版本命名空间。
- `MigrateConfigs` 把用户配置写到**当前目录** `config.json`（cwd 敏感，测试被迫切目录）。

## 一、版本表示

### 1.1 程序版本常量（来源 Q1 → 单一 Core 常量）
新建 `SimpleFFmpegGUI.Core/AppInfo.cs`：
```csharp
public static class AppInfo
{
    /// <summary>应用程序语义版本。数据库版本跟随它（DB schema 版本 = 该值）。发布时手工同步。</summary>
    public const string AppVersion = "2.0.1";
}
```
- 不取 `.NET AssemblyVersion`（自动递增、与 schema 无因果，会导致错位漂移）。
- 该常量即"当前发布版本"，也是新鲜库打标基线值。**实现时按本次发布的实际版本号确定**（计划示例 `2.0.1`）。

### 1.2 版本串形态（来源 Q2 → 纯数字三元组）
- 版本写成字符串 `"2.0.1"`，比较用 `(major, minor, patch)` **数值**元组（保证 `2.10.0 > 2.9.0`）。
- 忽略预发布（`-rc.x`）后缀；RC 发布以最终正式版数字落库。

新建 `SimpleFFmpegGUI.Core/Compatibility/VersionUtil.cs`：
```csharp
internal static class VersionUtil
{
    public static (int Major, int Minor, int Patch) Parse(string v);          // "2.0.1" -> (2,0,1)；非法抛 FormatException
    public static int Compare(string a, string b);                            // 组件级比较
    public static bool GreaterThan(string a, string b) => Compare(a, b) > 0;
    public static bool LessThanOrEqual(string a, string b) => Compare(a, b) <= 0;
}
```

### 1.3 `_MigrationHistory` 改为文本版本
```sql
CREATE TABLE IF NOT EXISTS _MigrationHistory (
    Id          INTEGER PRIMARY KEY AUTOINCREMENT,
    Version     TEXT NOT NULL,       -- 语义版本，如 "2.0.0"
    AppliedDate TEXT NOT NULL,
    Description TEXT NOT NULL
);
```
- 当前 DB 版本 = 所有记录中按 `VersionUtil.Compare` 最大的 `Version`（读全表取 Max，避免仅依赖插入顺序）。
- 旧版本（整数 `Version` 列）会被专门的一次规范化迁移改造（见 §3.3）。

## 二、迁移器模型

### 2.1 `IMigration`
```csharp
public interface IMigration
{
    /// <summary>该迁移把数据库升级到的目标程序版本（语义版本）。</summary>
    string Version { get; }
    string Description { get; }
    void Up(SqliteConnection conn, SqliteTransaction tx, MigrationContext context);
}
```
- 只标 **目标版本**，不设 `FromVersion`：等价于"从现在 DB 版本升级到此版本"。排序/唯一性由 runner 校验（`Version` 需唯一且升序）。
- 每个迁移的 `Up(conn, tx)` **必须与版本记录在同一事务**内提交（避免"已升级但未记录 → 重跑"的非幂等）。

### 2.2 排序与执行
Runner 应用所有满足 `迁移.Version > 当前DB版本`（且 `<= AppVersion` 防御上限）的注册迁移，按 `VersionUtil.Compare` 升序逐个执行。示例：注册表里有 `2.0.0`、`2.0.1`、`2.1.0`，库当前 `2.0.0` → 依次应用 `2.0.1`、`2.1.0`。

### 2.3 注册表
内置注册表固定于 `Compatibility/MigrationRegistry.cs`（静态有序集合），WebAPI 与 WPF 共用（两者都走 `AddFFmpegServices()`）。测试可注入自定义列表：
```csharp
public static class MigrationRegistry
{
    // 注意：MigrationNormalizeLegacyHistory 是"版本账簿修复"，由 MigrationRunner 在识别到
    // LegacyIntHistory 时显式执行，不放进 Default（否则会误触发重建版本表）。
    public static IReadOnlyList<IMigration> Default { get; } =
        new IMigration[] { new MigrationV1_1ToV2_0() };
}
```

## 三、Runner：状态分类与流程

新建 `MigrationRunner.cs`（`Duplicate`/`Sort` 校验 + 状态机）。入口：
```csharp
public static bool Upgrade(string connectionString, string configJsonPath,
                           IEnumerable<IMigration>? migrations = null)
```

### 3.1 状态分类（`classify`，根据 `sqlite_master` + 列信息）
| 状态 | 判据 |
|------|------|
| **空库/新鲜** | `sqlite_master` 中除 `sqlite_%` 外**无任何用户表** |
| **v1.1 旧库** | 无 `_MigrationHistory`；有 `Configs` 表**或** `Tasks.Arguments` 列存在 |
| **整数历史(遗留 v2.0)** | 存在 `_MigrationHistory` 且其 `Version` 列为 **INTEGER** |
| **文本历史(新系统)** | 存在 `_MigrationHistory` 且其 `Version` 列为 TEXT |
| **未知** | 其余（既非 v1 也非历史、或结构不符）→ 记警告、跳过，**不破坏** |

### 3.2 各状态流程
> **调用顺序**：调用方先执行 `EnsureCreated()`（对全新库建当前 schema；对已有表是 no-op），再调用 `Upgrade()`。
> 若对空库先 `Upgrade`，`StampBaseline` 会先建出 `_MigrationHistory` 这一张表，导致随后的 EF `EnsureCreated`
> 认为"库已建"而不再创建 Tasks/Presets/Logs——因此必须先 `EnsureCreated`。

| 状态 | 动作 |
|------|------|
| 空库/新鲜 | 建 `_MigrationHistory` 并插入基线 = `AppVersion`（独立事务）；返回 true。 |
| v1.1 旧库 | 备份一次 → 跑迁移链（缺省含 `MigrationV1_1ToV2_0` 及所有 `0.0.0 < Version <= AppVersion` 的迁移），每个迁移与版本记录同事务；返回是否跑了迁移。 |
| 整数历史(遗留) | 备份一次 → `MigrationNormalizeLegacyHistory`（由 runner 作为链首显式执行）：重建 `_MigrationHistory` 为文本列并写入 `"2.0.0"` → 继续 apply-pending（`> 2.0.0` 且 `<= AppVersion`）。 |
| 文本历史 | 读当前版本 → apply-pending（`> 当前` 且 `<= AppVersion`）；返回是否跑了迁移。 |
| 未知 | 警告、跳过、返回 false。 |

### 3.3 数据/迁移内容
- **`MigrationV1_1ToV2_0`**（目标 `"2.0.0"`）——把现有 `DatabaseMigrator.cs:101-271` 的 6 步迁移进来：
  - `MigrateSchema`（`Arguments → Parameters` 重命名，Tasks/Presets）
  - `MigrateTasksParameters` / `MigratePresetsParameters`（JSON 经 `PresetConverter.ConvertFromV1_1` 转换，失败行兜底空 `OutputParameters`）
  - `MigrateTaskTypeCustom`（`Type 3 → 99`）
  - `MigrateConfigs`（读旧 `Configs` 的 `DefaultProcessPriority`/`SnapshotSize` → 写入传入的 `configJsonPath`；**目标路径参数化**，把 cwd 依赖从迁移器内部上移到调用方；仍作为 v2 迁移的一个步骤保留）
  - `DropConfigsTable`
  - **去掉** `WriteMigrationHistory`（改由 runner 在每迁移成功后记录版本）
- **`MigrationNormalizeLegacyHistory`**（目标 `"2.0.0"`）——识别"命中整数历史"的库：将 `_MigrationHistory` 改为文本 `Version` 并写入 `"2.0.0"`。**绝不能重跑 v1→v2**（`Arguments` 已改名）。据此该库判定"已在 2.0.0"，后续仅跑 `> 2.0.0` 的迁移。

### 3.4 备份
仅当**确定有迁移将运行**时备份一次：`{dbPath}.backup.{yyyyMMddHHmmss}`（沿用现有命名，失败仅告警不中断）。

## 五、调用点改造

`MigrationRunner.Upgrade` 需要 `configJsonPath`（迁移出的用户配置要写入运行时实际读取到的 config.json）。
生产上 `ConfigService`/`Config` 都用**相对 cwd** 的 `"config.json"` 读写，因此两宿主传 `cwd/config.json`（与旧行为一致，
只是把 cwd 依赖从迁移器内部上移到调用方，迁移器本身不再触碰当前目录）。

**顺序改为先 `EnsureCreated()` 再 `Upgrade()`**（见 §3.2 顶部说明）：
- **WebAPI** `Program.cs`：`MigrateDb`（约 201 行）改为 `MigrationRunner.Upgrade(connStr, Path.Combine(Environment.CurrentDirectory, "config.json"))`；
  `InitializeDatabase`（约 89 行，`EnsureCreated`）调到 `MigrateDb` 之前执行。
- **WPF** `App.xaml.cs`：`context.Database.EnsureCreated()` 在 `MigrationRunner.Upgrade` 之前；
  `configJsonPath = Path.Combine(Environment.CurrentDirectory, "config.json")`。
- **WebTest** `CompatibilityMigrationTests`：改走 `MigrationRunner.Upgrade`，传临时目录的 `config.json`（无需切 cwd）；WebTest 的 `SimpleFFmpegWebApplicationFactory`/fixture 需在测试库上显式调用 `MigrationRunner.Upgrade` + `EnsureCreated`。

## 六、测试策略

沿用 xUnit + FluentAssertions，中文注释。

1. **保留** `CompatibilityMigrationTests.MigrateV1_1Database_ShouldSucceed`：构造 v1.1 schema（仍可复用现有 `CreateV1Database`），改走新 runner，断言迁到注册表最高版本、`_MigrationHistory` 为文本版本、`Configs` 已删、列已改名、Custom 3→99、JSON 旧字段名消失、config.json 键值对完整。
2. **新增合成迁移证堆叠**：测试内注册一个**虚构** `MigrationV2_0_1`（目标 `"2.0.1"`，做一次简单 schema 变更，如给 `Tasks` 加一列或改某默认值），喂入"已到 2.0.0"的库 → 断言被逐级升级到 `"2.0.1"`，证明"跟随程序版本"的管道可叠加。
3. **空库打标测试**：全新空库 → `Upgrade` 后 `_MigrationHistory` 有一条 `Version = AppVersion` 的基线，随后 `EnsureCreated` 不报错。
4. **整数历史规范化测试**：构造一份"已升级到 v2.0（整数 Version=1、`Arguments` 已改名）"的库 → 断言首次不抛异常、`_MigrationHistory` 转为文本并戳 `"2.0.0"`、**不重跑 v1→v2**（`Arguments` 列不存在、无异常）。
5. **幂等测试**：连续两次 `Upgrade`，第二次返回 false（无待跑迁移）。

## 九、已定决策汇总（供复核）

| 决策 | 结论 |
|------|------|
| 迁移驱动器 | 真·注册表 runner（`IMigration` 按目标版本升序堆叠） |
| 版本来源 | Core 单一常量 `AppInfo.AppVersion`（语义版本，非 AssemblyVersion） |
| 版本形态 | 纯数字 `major.minor.patch`，组件级比较，忽略预发布 |
| 无历史库基线 | 嗅探识别 v1；**空库打标**为 `AppVersion`；杜绝"新库误判 v1" |
| 事务作用域 | 每迁移各自事务，版本记录与 `Up` 同事务；备份仅"有迁移将运行时"一次 |
| config 迁移 | 保留为 v2 迁移步骤，目标 `config.json` 路径参数化，把 cwd 依赖上移到调用方 |
| 测试 | 保留 v1→v2 主路径 + 新增合成 v2.0.1、空库打标、整数历史规范化、幂等 |
| 旧模型组织 | 迁入 `Compatibility/Legacy/V1_1/` |
